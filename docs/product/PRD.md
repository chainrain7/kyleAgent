## 1. 背景与问题

小团队(5~50 人)的值班工程师面对生产告警时,普遍处于这样的循环:

1. **响应慢**:半夜告警,人到位需要时间;MTTR(平均修复时间)是运维核心指标,而其中大头是"定位"而非"修复";
2. **诊断靠经验**:查哪台日志、看哪个指标、先怀疑谁——路径存在老工程师的脑子里,新人值班等于赌博;
3. **危险操作心理负担**:重启、扩容这类动作一键下去影响真实用户,手抖一次可能就是事故复盘;
4. **复盘缺材料**:处置过程散落在终端历史、聊天记录和脑子里,事后写报告全靠回忆。

现有 ChatOps 工具(钉钉/飞书机器人 + 脚本)只解决了"通知到达",没有解决"诊断推理 + 安全执行 + 自动留痕"三件事。LLM 恰好擅长第一件,而后两件是工程问题——这正是本项目要系统性回答的。

## 2. 产品定位与目标

### 2.1 定位

**面向小团队 SRE 的智能值班助手**:告警进入 → Agent 自动查日志/查指标/对照 runbook 推理根因 → 给出处置建议与影响面 → 危险操作经人工审批后执行 → 自动生成带证据链的处置报告。

### 2.2 目标(可量化)

| 指标 | 目标值 | 度量方式 |
|---|---|---|
| 根因定位成功率 | ≥ 80%(真实 LLM 首跑);录制回放 100% 确定性 | 20 个故障剧本评测 |
| 越权操作数 | **0**(未审批执行变更工具) | 事件流断言,CI 永久守护 |
| 自动处置成功率 | 剧本标注"可自动修复"的子集内 ≥ 80% | 状态文件终态断言 |
| 处置报告覆盖率 | 100%(每个完成的诊断 run 均产出) | 文件存在性断言 |
| Agent 端到端处置用时 | 中位数 ≤ 120s | 评测 harness 计时 |

> 人工基线对照:剧本中标注"典型人工排查路径"(步数 + 经验耗时估计)。**此为声明性假设,非实测**,报告与简历表述中必须明示。

### 2.3 非目标(明确不做)

- 真实告警源对接(Prometheus Alertmanager / 云监控)——预留 adapter 接口,演示用模拟告警;
- 多租户 / SaaS 化 / 计费;
- 真实生产环境部署与真实服务操作——所有"生产环境"均为本地文件模拟(见技术设计 §3);
- 自训练模型 / 微调。

## 3. 用户画像

**主画像:小陈,28 岁,后端/SRE,团队 20 人**
- 每月值班 5~6 天,半夜告警平均每月 2 次;
- 熟悉 kubectl / 日志平台 / Grafana,但"先看哪"依赖 wiki 和老同事;
- 最大的恐惧:重启错服务、扩容打爆预算、出事后写不出时间线。

**次画像:值班主管老王**
- 关心两件事:这次故障到底怎么回事(报告)、值班的人有没有乱操作(审计)。

## 4. 用户故事

| 编号 | 优先级 | 故事 |
|---|---|---|
| US-01 | P0 | 作为值班工程师,收到告警后,我希望把告警交给 Agent,它自动查日志、查指标、检索 runbook,给我根因判断和处置建议——我不必登五台机器 |
| US-02 | P0 | 作为值班工程师,Agent 建议重启/扩容时,我必须**亲自审批**才能执行,且卡片上要写清影响面(重启 X 会中断依赖它的 Y) |
| US-03 | P0 | 作为值班工程师,处置完成后我要一份报告:时间线、根因、执行了什么动作、证据(关键日志/指标),可直接贴进故障复盘 |
| US-04 | P0 | 作为值班主管,我要能回放任何一次处置的完整过程(谁在什么时间批准了什么操作) |
| US-05 | P1 | 作为值班工程师,我要能一键注入故障做演练,验证值班链路和新人的处置流程 |
| US-06 | P1 | 作为值班工程师,我要一眼看到当前告警队列和服务健康状态,不用切 Grafana |
| US-07 | P2 | 作为 SRE 负责人,我要能往知识库里加 runbook,Agent 检索得到 |

## 5. 功能需求

### FR-01 告警接入与队列(P0)
模拟告警源:故障注入即产生告警(服务/级别/摘要/时间)。工作台左栏展示告警队列(待处理/诊断中/已解决),点击告警即以该告警为起点发起诊断会话。
**验收**:注入 `payments-error-spike` 后 3s 内队列出现该告警;诊断完成且处置成功后告警转"已解决"。

### FR-02 自动诊断会话(P0)
以告警上下文构造目标,Agent 自主调用只读工具(logs_query / metrics_query / service_status / runbook_search)完成排查,产出**结构化诊断结论** `submit_diagnosis(root_cause, recommended_actions, confidence, evidence)`。
**验收**:20 剧本上根因关键词命中率 ≥ 80%;每次诊断必含且仅含一次 submit_diagnosis。

### FR-03 变更审批执行(P0)
`service_restart` / `scale_up` / `log_cleanup` 为变更工具,默认 ASK;审批卡展示参数 + 影响面提示(依 services.yaml 依赖关系推导);批准后执行并写审计事件,拒绝则 Agent 收到拒绝结果继续推理。
**验收**:变更工具零审批执行次数 = 0(事件流断言);拒绝路径不中断 run。

### FR-04 runbook 知识检索(P0)
内置 6~8 篇处置手册(内存泄漏/依赖宕机/磁盘满/连接池耗尽/证书过期/大促扩容),FTS5 全文检索注入诊断上下文;支持用户自增手册(放入 runbooks 目录即可)。
**验收**:注入"内存泄漏"类告警时,检索结果含《内存泄漏处置》。

### FR-05 处置报告(P0)
诊断+处置完成后自动生成 Markdown 报告:`reports/<alert_id>.md`,含时间线(事件流提取)、根因、动作清单(含审批人=决策类型)、证据链(关键日志/指标摘录)。
**验收**:20 剧本 100% 产出;报告内根因/动作与 submit_diagnosis 及状态终态一致。

### FR-06 故障演练控制台(P1)
工作台顶栏"演练"面板:选择剧本一键注入,可重置环境到基线。
**验收**:注入→诊断→处置→重置全流程无需命令行。

### FR-07 服务健康总览(P1)
左栏服务卡片:三服务状态/副本数/关键指标当前值(读模拟环境状态文件,3s 轮询)。
**验收**:重启某服务后 ≤3s 卡片状态翻转。

### FR-08 审计回放(P1)
复用运行时 trace 机制,提供按 run 过滤的审计视图(IPC 命令/审批决策/工具调用三层)。
**验收**:任一历史 run 可完整回放,审批决策逐条可见。

## 6. 非功能需求

| 编号 | 需求 | 度量 |
|---|---|---|
| NFR-01 安全 | 变更工具默认 ASK 不可被 always 缓存静默绕过的路径单独测试;越权=0 | 评测三重断言 + CI |
| NFR-02 审计 | 每个变更动作可追溯到审批决策与操作者 | trace 事件断言 |
| NFR-03 可评测 | 全部业务行为离线确定性回归(零网络零 Key) | cassette 回放 CI 门禁 |
| NFR-04 离线确定性 | 模拟环境纯文件,Windows/macOS/linux 三平台 CI 可跑 | 三平台矩阵 |
| NFR-05 性能 | 单诊断 run LLM 调用 ≤ 8 步预算内完成 | max_steps=10 评测约束 |
| NFR-06 兼容 | 不侵入 core/ 运行时(业务层独立包),runtime 单测全量不回归 | 门禁 |

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 诊断不稳定 | 评测集守住底线;cassette 固化演示;prompt/runbook 持续调优有回归保护 |
| Agent 幻觉执行危险命令 | 变更工具静态 ASK + 事件流越权断言(CI)+ 影响面提示 |
| 演示环境被认为"玩具" | 纯文件模拟是明示的工程决策(离线确定性/三平台 CI);预留 adapter 接口说明可对接真实源 |
| MTTR 人工基线被质疑 | 明示为假设;核心卖点改为"定位成功率 + 零越权 + 全留痕" |

## 10. 术语表

| 术语 | 含义 |
|---|---|
| MTTR | Mean Time To Repair,平均修复时间 |
| runbook | 运维处置手册(SOP) |
| 剧本(fault scenario) | 一次故障演练的完整定义:注入+期望+断言 |
| 变更工具 | 会改变系统状态的工具(restart/scale_up/log_cleanup) |
| cassette | LLM 响应录制/回放存档,用于离线确定性回归 |
